# 第一版计划

## 产品与范围

面向需要回复私人聊天的用户。输入双人文字聊天，整理可追溯的上下文，提供不同立场的建议，用户调整语气后自行复制。支持中文和英文；当前演示使用中文界面与英文回复。

目标流程：粘贴记录 → 确认说话人 → 提取并纠正上下文 → 选择回复方向 → 调整风格 → 查看新增承诺 → 复制。

第一版不包含消息自动发送、国籍性格推断或长期人格画像。Emoji 解读只能给出有依据的可能解释。

## 三个验收场景

1. 朋友约周六晚餐：用户此前只说可能有空。提供答应、有条件答应、拒绝三种方向；答应版本必须提示新承诺。
2. 熟人请求周五帮忙：用户此前说周五忙。拒绝的柔和版本仍须拒绝，不得编造理由；提出周日替代方案须提示周日未确认。
3. 对方回复 Sure 🙂：文字表示同意，但不能确认情绪或时间。提供确认时间、简单致谢、降低时间压力三种方向，不将 Emoji 当成情绪证据。

## 目标数据契约（当前实现见 core.py）

- Message: id, speaker(self/other), text, timestamp(可空)。
- ContextItem: id, kind(fact/question/commitment/uncertain), text, source_message_ids, status(extracted/user_confirmed/user_corrected)。
- Preferences: length, directness, warmth, emoji；本次设置覆盖默认设置。
- Reply: direction, text, addressed_question_ids, introduced_commitments, assumptions, evidence_ids。
- Check: type(stance_conflict/unsupported_fact/missing_answer/new_commitment), explanation, related_message_ids。

服务端验证消息引用存在；不将模型输出当作可信 HTML。将用户纠正与模型提取分开保存。聊天中的指令属于待分析数据，不能覆盖系统规则。不得记录原始聊天到普通访问日志。

## 模型处理流程（已编码，待真实联调）

解析消息与说话人 → 结构化上下文提取 → 用户纠正 → 按立场生成候选 → 检查立场与无依据事实 → 展示建议及检查结果。

检查结果只是辅助，不能宣称确保语义完全正确。允许用户主动改变原先承诺，并明确显示变化。

## 评估设计

先制作约 30 个独立虚构案例：邀约、拒绝、改期、请求帮助、模糊回复，每类约 6 个，覆盖中英文。每例标注证据消息、必须保留的含义、允许的新决定和不可编造的信息。开发样例与保留评估样例分离。

同一模型、同一聊天、同一偏好比较：A 直接输入完整聊天并使用合理提示词；B 结构化提取后生成；C 加入检查步骤。记录实际模型版本、提示词版本、调用次数、耗时及可用的 token 用量。

人工隐藏来源评判：事实与引用正确性、立场保持、语气符合度、歧义处理、无依据新增事实、实际可用性。分歧保留并复核。报告分子/分母与失败案例，不能用预置演示输出证明模型有效。
